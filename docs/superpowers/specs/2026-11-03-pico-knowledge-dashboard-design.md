# Pico: база знаний Confluence и Jira

Дата: 03.11.2026. Статус: опубликовано 03.11.2026 (загрузчик 57c8c64, ассеты 66c7e83); локальные проверки и ревью завершены, Citrix-приёмка источников не завершена.

## Задача

Отдельный дашборд Jira с чатом Pico. Пользователь задаёт вопрос обычным текстом; помощник ищет в Confluence и Jira, читает найденные материалы, отвечает со ссылками на прочитанные источники. Первый сценарий: «Как правильно завести задачу DevOps по нашим правилам?» Существующий помощник создания задач продолжает работать отдельно.

## Подключение: обязательный первый этап

Уточнение пользователя 03.11: вместо изменения CORS выбран локальный сервер подключения в VDI, запускаемый PowerShell из опубликованного GitHub-скрипта. Разрабатывается только сервер и диагностическая страница, не полный чат. Страница работает на localhost в одном origin с read-only API; upstream фиксирован параметром при запуске. Авторизация None / явно выбранные Windows credentials / PAT через скрытый ввод в процессе. Подробности и ограничения: `docs/knowledge-bridge.md`. Этот вариант не даёт виджету на домене Jira автоматический доступ к localhost. Следующая интеграция чата будет размещаться на локальной странице и потребует отдельной проверки LLM/Jira.

Дополнительная проверка макросов 03.11.2026: в Citrix открыт редактор пустого черновика в пространстве СДКУ-Стандарт и каталог «Другие макросы». Поиски HTML, script, iframe не показали результатов. В категории «Внешний контент» видны JIRA, RSS Feed, Table from CSV, Table from JSON, Коннектор виджета. Последний предназначен для поддерживаемых внешних сервисов, а не подтверждённого запуска нашего bootstrap: https://confluence.atlassian.com/conf719/widget-connector-macro-1157466963.html. Встраивание чата без администратора не подтверждено; рекомендовать перенос в Confluence как готовое решение нельзя. Ничего не опубликовано, код в страницу не вставлялся. При открытии редактора Confluence использует черновик. Во время проверки появились неожиданные переходы (другой макрос и другой draftId); управление прекращено, закрытие черновика не подтверждено. Доказательства: `~/.codex/citrix-prod-runs/pmi-prod-20261103-153732/`, `pmi-prod-20261103-153745/`, `pmi-prod-20261103-153758/`, `pmi-prod-20261103-153810/`, `pmi-prod-20261103-153904/`.

1. Предпочтительный первый вариант для текущего статического дашборда — разрешить чтение Confluence с origin Jira через reverse proxy и использовать текущую пользовательскую сессию. После изменения администратором проверить JSON, фактического пользователя и ограничения доступа. Точный origin: `https://jira.dc-prod.tn.corp`; только необходимые GET/OPTIONS, credentials, Vary: Origin. Не использовать wildcard origin с credentials.
2. Если такой доступ не разрешён — согласованный серверный адаптер, доступный дашборду в origin Jira, с OAuth/Application Links от имени пользователя. Наличие Application Links само по себе не означает наличие универсального browser proxy. Сначала найти и проверить доступный серверный механизм, затем определить его endpoint. Не выдумывать существующий endpoint.
3. PAT является запасным способом авторизации серверного адаптера, но не исправляет CORS. Для многопользовательской работы нельзя применять общий привилегированный токен ко всем пользователям. Персональные токены наследуют права владельца; read-only ограничение обеспечивает наш адаптер, а не выдуманный scope PAT. Токены не хранятся в JS/CDN, localStorage, переписке или LLM-контексте.

До подтверждения одного пути production-интеграция заблокирована; можно отдельно делать локальные модули на заглушках, но нельзя объявлять подключение работающим. В этой задаче не меняются настройки инфраструктуры и не создаются токены.

Основания: [PAT Atlassian](https://confluence.atlassian.com/enterprise/using-personal-access-tokens-1026032365.html), [CORS Confluence 7.15+](https://support.atlassian.com/confluence/kb/configure-cors-for-specific-urls-in-confluence-715/), [Application Links OAuth](https://confluence.atlassian.com/applinks/oauth-security-for-application-links-774045732.html), [Confluence REST](https://developer.atlassian.com/server/confluence/rest/latest/).

## Поведение и границы первой версии

- Компактная шапка: название, выбор пространств Confluence/проектов Jira, настройки, полный экран. Основное место занимает чат; снизу обычная область ввода с отправкой/остановкой.
- Pico использует существующее подключение LLM и vendor runtime 1.4.0. Новый провайдер, индексатор, векторная база не нужны.
- Инструменты только чтения: search_confluence, read_page, search_jira, read_issue. Поиск возвращает до 20 результатов за вызов и явный курсор продолжения. Чтение возвращает части до 8000 символов, total/nextOffset и предупреждения о неполном содержимом. Не обещать полноту макросов и вложений: первая версия читает текст, списки, таблицы; неподдерживаемые блоки отмечает.
- Скилл «Корпоративные правила» задаёт стратегию поиска, чтения и проверки источников. Текст найденных страниц — данные, а не инструкции на выполнение новых действий. Системные правила инструментов пользовательский скилл не отменяет.
- Ответ содержит проверяемые ссылки на фактически прочитанные фрагменты, заголовок и дату/версию источника. Поисковый сниппет не считается прочитанной страницей. При конфликте документов помощник показывает расхождение. При нехватке данных говорит, чего не удалось получить.
- Доступ к источникам ограничен текущим пользователем и выбранными пространствами/проектами. Ограничения применяются кодом и сервером, не только промптом. Нет инструмента произвольного HTTP/URL; безопасное построение CQL/JQL.
- Пределы одного хода: 8 вызовов модели, 12 вызовов инструментов, 180 секунд. Бюджет контекста берётся из существующих настроек; при отсутствии — 32768 с резервом 4096. Оценка токенов явно помечена оценкой. Компрессия старых ходов явная, полный текст диалога не уничтожается.
- Кэш доказательств изолирован по пользователю, origin и подключению, находится в памяти. Настройки и история используют отдельное пользовательское пространство хранения. Восстановленные ссылки помечаются историческими и перед новым ответом перечитываются. Смена пользователя очищает доступ к предыдущей сессии.
- Ошибки входа, 403, CORS/сети, 429 и неполной загрузки понятны пользователю. Редирект на HTML-страницу входа не трактуется как успешный JSON. Остановка отменяет текущие запросы; старый ответ после смены области поиска не попадает в новый диалог.
- Публикация отдельным bootstrap/runtime/CSS с закреплением коммита. AMD-имена `_ujgKnowledgeAssistant` и `_ujgKA_*`; встроенный Pico получает отдельное AMD-имя на сборке, чтобы два виджета работали на одной странице.
- В первой версии нет создания/изменения Jira-задач или Confluence-страниц. Поиск знаний не переносит разрешение на создание тестового тикета из прежней задачи.

## Приёмка

На заглушках: поиск → чтение → ответ с источниками, пагинация, отказ в доступе, конфликт документов, вредоносный текст страницы, отмена, смена пользователя, длинная страница и ограничение контекста. Лично проверить интерфейс 1440/390 px и совместное размещение с помощником задач.

В Citrix: сначала подтвердить чтение JSON и права пользователя, затем найти реальную страницу правил DevOps; сравнить извлечённые шаблоны с оригиналом. Запуск LLM — явным действием пользователя. Проверить, что ответ различает три шаблона, обязательные сведения и исключения, не выдаёт старый скриншот за актуальный источник. До этих действий приёмка production остаётся открытой.

## Актуальное решение после проверки SSH-туннеля

Виджет остаётся отдельным дашбордом Jira. Python bridge на Linux слушает loopback и доступен из Windows VDI через SSH forwarding; /health подтверждён 200 JSON. Confluence routes и in-memory getToken описаны в уточнении плана; Jira читается через текущую сессию виджета. Прежнее предположение о размещении полного чата на локальной странице отменено прямым запросом пользователя установить виджет в Jira. Авторизация Confluence, браузерный fetch и ответы LLM ещё не приняты. Локальную реализацию на заглушках можно завершать независимо от отсутствующего PAT.
