# Динамика замечаний: загрузка, история и дневные отчёты

Статус: согласовано пользователем 27.09.2026, реализован первый объём,
локальная приёмка пройдена; read-only Citrix ожидает восстановления сессии.
Результат: `docs/import-performance-acceptance-2026-09-27.md`.
Уточнение реализации по измерениям: существующие снимки задач сохраняются,
новый store хранит только ограниченный кеш отчётов. Основной render служит
консервативной границей версии данных и очищает кеш; отдельные индексы
сырой истории не добавлялись, поскольку расчёт занимает 23–32 мс.
Основание: запрос 27.09 на быстродействие и понятную иерархию загрузки,
хранения событий и переключения истории. Исходный код: `0fb73a2`.

## Решение

Разделить получение данных Jira, хранение проверенной истории, расчёт
дневного среза и отображение. Развивать существующий виджет поэтапно,
сохраняя реестр, экспорт, фильтры, сроки, команды и LLM-подключение.
Не начинать с переписывания приложения, нового фреймворка или сервера.

Варианты:

| Подход | Польза | Ограничение |
| --- | --- | --- |
| Только локальные ускорения DOM и AI | Меньше задержек при небольшой правке | Не решает управление очередью, повторное чтение и понятность состояния |
| Разделённый конвейер внутри виджета, рекомендуется | Управляемая загрузка, повторное использование историй и отчётов, постепенная проверка | Потребуются явные версии данных и тесты гонок |
| Серверный сборщик с общей БД | Общая история и отчёты для всех, сбор без открытого браузера | Отдельный проект: размещение, права, доступ к Jira, хранение, эксплуатация |

Первый объём: второй подход с ограниченным кешем в памяти вкладки.
Серверный сборщик не входит в объём. Полноценная многопользовательская
система в будущем не должна изображаться браузерным кешем одного человека.

## Что Сейчас Связано

- `main.js:onLoadRegistry` получает исходные истории, затем детей партиями
  по 100. `api.js:getProjectIssues` уже постраничный, но вместе с карточками
  запрашивает changelog. Есть явный предел 1000 исходных историй.
- `main.js:onLoadActivityHistory` дочитывает историю до трёх задач одновременно.
  Прогресс ограничен интервалом 500 мс, но обновляет общий render.
- `rendering.js:render` очищает корень. `activity-ui.js:render` сбрасывает
  кеш расчёта. Обновление прогресса затрагивает весь дневной отчёт.
- Смена дня во время загрузки не меняет текущую очередь сразу; нужная
  дополнительная очередь проверяется после окончания предыдущей.
- Новый отчёт немедленно готовит полный LLM-контекст, даже с закрытым окном.
- `capture` уже проверяет полноту, непротиворечивость цепочек и времена.
  Это сохраняемый доменный контракт, не повод ослаблять диагностику.

## Иерархия Данных

1. Область: адрес Jira, проверенный пользователь, проект, эпик.
2. Состав замечаний: исходная история и её текущие связанные задачи.
3. Проверенный снимок каждой задачи: поля, changelog, отдельное покрытие
   комментариев и трудозатрат, время чтения и диагностические признаки.
4. Нормализованные события: ссылки на задачу/запись/поле, автор, время,
   значения до и после; индексы по задаче и календарному дню МСК.
5. Дневной отчёт: метрики, группы, переходы и покрытие на определённой
   версии состава, истории, настроек команд и данных Excel.
6. Представление: фильтры журнала, сортировка, ширины, раскрытие, прокрутка.

История хранится по задаче один раз, а не копируется для каждого дня.
Связь задачи с несколькими замечаниями не дублирует глобальный счётчик событий.
Исходные события сохраняются; объединение действий за минуту остаётся
только способом отображения. Неизвестная история связей не восстанавливается
из текущего состава: прежняя оговорка остаётся видимой.

## Границы Модулей

| Часть | Ответственность | Не делает |
| --- | --- | --- |
| `api.js` | Узкие операции чтения, постраничность, управляемая отмена где доступна | Не считает метрики и не управляет DOM |
| Новый `activity-loader.js` | Очередь, дедупликация запросов, приоритет выбранного среза, отмена, прогресс | Не хранит HTML и не объявляет историю полной |
| Новый `activity-store.js` | Снимки задач, их версии, принадлежность области, индексы и ограничение кеша | Не обращается к Jira и не выбирает UI-фильтры |
| `activity.js` | Проверка данных и детерминированный расчёт отчёта | Не загружает данные и не перерисовывает интерфейс |
| `activity-ui.js` / `rendering.js` | Независимые обновления прогресса, отчёта и таблицы | Не запускают полный сбор от любого изменения DOM |
| `activity-ai-ui.js` | По явному действию фиксирует срез для LLM | Не готовит большой контекст при обычной смене даты |

Сначала выделить существующее поведение за эти границы, без универсальной
системы плагинов, глобальной шины событий или второго хранилища истины.

## Поведение При Переключении

### Первый Вход

1. Определить пользователя и область. Получить состав исходных историй и детей.
2. Принять уже пришедшие полные истории. Дочитать только отсутствующие,
   неполные или нуждающиеся в актуализации снимки через одну очередь.
3. Проверить и проиндексировать новые версии. Подготовить выбранный день.
4. Опубликовать согласованный отчёт. Показать время среза и покрытие.

Ранние частичные результаты допустимы только с явным «предварительно».
Предыдущий подтверждённый отчёт не смешивается с частями нового:
либо показан прежний снимок с его временем, либо отдельный предварительный.

### Смена Дня

- Сразу переключить выбранную дату и статус загрузки на неё.
- Если для новой даты ещё нет отчёта, показать состояние подготовки,
  а не старые цифры под новой датой. При обновлении той же даты можно
  оставить прежний отчёт с явным временем его среза.
- Есть подходящий дневной отчёт нужной версии: показать из кеша.
- Есть вся история, но нет расчёта дня: рассчитать без запросов Jira.
- Истории недостаточно: дать нужным чтениям приоритет, показать покрытие.
- Не начатые работы только для прежнего выбора убрать из активной очереди.
  Совпадающие чтения переиспользовать. Ненужные активные запросы отменять,
  если транспорт это поддерживает; в остальных случаях изолировать ответ.
- Ответ той же области может пополнить кеш после проверки, но не менять
  выбранную дату и её экран. Старое вычисление не заменяет новый отчёт.
- Уход в другой проект/эпик/пользователя полностью отделяет старую очередь.

Идентификатор выбора экрана и версия данных являются разными сущностями.
Отмена выбора не обязана уничтожать полезный снимок той же области.
У области свой номер поколения, у чтения задачи свой номер запроса:
поздний ответ не перезаписывает уже принятую более новую версию задачи,
даже если на экран напрямую не выводится. Не считать время прихода ответа
доказательством новизны. Несовместимые версии сохраняют диагностику,
а не объединяются молча.
Истории обычно нужны целиком: текущий API не позволяет считать произвольный
день полным только потому, что загружены изменения с этой датой.

### Обновление

«Обновить» заново проверяет состав и текущие карточки, затем обновляет
зависимые истории и отчёты. Смена даты сама по себе не означает обновление
Jira. На повторном входе проверяется актуальность области; старый кеш
можно показать до проверки только с явной отметкой времени и состояния.
Время среза уже построенного отчёта фиксировано. Ход часов сам по себе
не порождает непрерывного перечитывания всех задач; новое обновление создаёт
новую версию среза. Переход через полночь отдельно обновляет расчёт просрочки.

Разделение лёгкого чтения полей и тяжёлой истории делать отдельным шагом
после замеров. `updated` является сигналом для проверки, не универсальным
доказательством неизменности данных. Не подменять `capturedAt` старой истории
новой датой без подтверждения совместимости снимков и покрытия.
Если этот контракт нельзя доказать по доступным данным, перечитать задачу.

Нельзя отбирать события прошлого дня только по JQL `updated` этого дня:
задача могла обновиться позже и всё равно содержит нужные прошлые события.

## Прогресс Для Пользователя

Над итогами компактная строка этапов. В ней отдельно видны состав,
чтение истории и готовность отчёта. Пример условных значений:

> 24 сентября · Состав: 250 замечаний / 1000 задач · История: 760/1000 ·
> Читаются: 3 · Ошибок: 2 · Отчёт: предварительный

Другой пример:

> 23 сентября · Из кеша · Срез 27.09, 12:04 МСК · Полнота: 1000/1000

Число завершённых запросов не равно числу полных историй: показывать это
раздельно. Пока состав неизвестен, не рисовать выдуманный общий процент.
Нажатие на этап открывает детали: какая задача читается, не хватает страниц,
ошибка доступа/сети, противоречивая история. Есть «Повторить ошибки»;
нет бесконечного автоматического повторения. Остальные данные доступны.

Состояния этапа: ожидает, выполняется, готов, частично, ошибка, отменён.
«Загрузка остановлена» не должна выглядеть как «данных нет».
Полнота историй, свежесть снимка и покрытие всего проекта показываются
раздельно. Лимит 1000 исходных историй не прятать за полными историями
загруженной части; увеличение/снятие этого лимита не входит в оптимизацию.

## Кеш И Корректность

- В первом объёме история живёт только в памяти вкладки. localStorage
  остаётся для пользовательских настроек, а не тысяч текстов событий.
- Кеш разделён по Jira и пользователю; области проекта/эпика не смешиваются.
  При неизвестной личности не переиспользовать данные другого контекста.
- У снимка есть версия содержимого, фактическое время чтения, покрытие и
  диагностика. Неполный результат не становится полным из-за повторения
  запроса. Не сшивать произвольные ответы по одному лишь ID.
- Новая версия истории заменяет старую версию задачи согласованно,
  с пересборкой её индекса. Простое добавление «новых» записей недостаточно:
  возможны исправления, удаление/недоступность записей и смена прав.
- У отчёта ключ включает область, день, версии состава/снимков, команд,
  сопоставлений и журнала Excel, глобальный фильтр компонентов и день
  расчёта просрочки. Фильтры колонок влияют только на журнал представления.
- На старте консервативно сбрасывать дневные отчёты области при изменении
  снимков; более точное обновление зависимостей допускается после тестов.
  Старый день тоже зависит от более поздних переходов при восстановлении
  статуса, поэтому инвалидировать только день нового события нельзя.
- Кеш ограничен: небольшое число последних дневных отчётов, один активный
  набор задач. Предел памяти выбрать по нагрузочному замеру. При превышении
  не скрывать события: удалять только вычисляемый кеш, а ограничение исходного
  набора явно обозначать и согласовывать отдельно.
- Отказ в доступе/смена пользователя не оставляет старые данные как актуальные.
  Ошибка сети оставляет прошлый снимок доступным только с его прежней датой.
- Экспорт и LLM используют зафиксированную версию показанного среза.
  Смена дня изолирует AI-разговор, обновление отмечает прежний ответ устаревшим.

Хранение между перезапусками через IndexedDB возможно вторым этапом,
но отдельно требует правил очистки, срока хранения и безопасной проверки
пользователя/прав. Это не общая БД команды; автоматически не включать.

## Порядок Оптимизации

1. Нагрузочный стенд: три дня по 900 событий, 250 замечаний и 1000 задач,
   реальный конвейер capture/summarize/UI на воспроизводимых заглушках.
2. Убрать подготовку полного AI-контекста из обычного просмотра; подготовка
   при открытии/запуске AI с сохранением контроля версии и отмены.
3. Отделить прогресс от render всего виджета. Сохранять DOM таблицы,
   прокрутку, раскрытия, фокус и черновик фильтра во время фонового чтения.
4. Ввести единый координатор загрузки и ограниченный кеш снимков/отчётов.
   Смена дня выбирает нужную работу, а не ждёт всю прежнюю очередь.
5. Измерить и, если значимо, убрать повторные сканирования/сортировки через
   индексы по задаче и дню. Проверять равенство результатов до и после.
6. Если построение/расчёт всё ещё блокирует экран, дробить работу на порции.
   Worker или виртуализация таблицы только после отдельного доказанного
   выигрыша и проверки совместимости с Citrix, переносами строк, поиском,
   фильтрами, раскрытиями и экспортом. Не обещать их как готовое решение.

## Приёмка

- До/после на одном наборе: начальная загрузка, прогресс при медленном API,
  тёплая и холодная смена дня, фильтры, сортировка, детали, прокрутка.
- Браузерные медиана/p95/максимум; отдельно сетевое ожидание, CPU расчёта,
  AI-подготовка, DOM и следующий кадр. Предварительные цели: тёплая смена
  дня p95 до 300 мс и отсутствие повторных зависаний дольше 100 мс на
  прогрессе. Это цели для фиксированного тестового окружения, не измерения
  и не гарантия времени Jira/Citrix.
- Три дня по 900+ исходных событий, затем больший контрольный набор.
  Сверить точные ID, группы, метрики, переходы, границы суток и экспорт;
  не добиваться скорости скрытым отсечением данных.
- Быстро переключить дни A/B/C при незавершённых запросах: на экране
  остаётся C, нет повторных одинаковых чтений и поздней подмены отчёта.
- Проверить изменения истории, команд, связей, компонентов, сроков Excel,
  переход через полночь, пустой день, сетевую ошибку и отмену загрузки.
- Проверить отсутствие живых вызовов LLM и записей Jira в тестах.
- Независимое ревью изменений и личная проверка локального UI; изменение
  рабочего виджета дополнительно принимается read-only в Citrix.
  Недоступный Citrix оставляет прод-приёмку открытой.

## Самопроверка Проекта

Не смешаны загрузка и готовность данных; отмена очереди не потеряет полезный
результат той же области; кеш не маскирует неполноту/устаревание; старые дни
пересчитываются при новых версиях, сроки остаются «на сегодня»; история не
режется датой updated; новые провайдеры и серверы не добавляются.
Остаются проверяемые риски: свойства текущего Jira API, реальная стоимость
DOM/AI, память больших описаний и доступность отмены составных запросов.
Их проверяет первый этап, а не предположение в архитектуре.
