# Последовательная облегчённая загрузка Import

Пользователь 26.10 подтвердил предложенную схему: лёгкие страницы реестра,
затем отдельная частичная догрузка тяжёлых данных. Причина: первая страница
200 историй с changelog/comment/worklog достигает клиентского предела 30 с.
HTTP 200 сам по себе не доказывает получение полного ответа до тайм-аута.

## Выбранный подход

Первый этап читает страницы по 50 задач: поля реестра, включая description,
duedate и связи, без changelog, comment и worklog. После полного чтения
историй и связанных задач публикуется базовый реестр. Старый полный набор
строк сохраняется при сбое базового этапа; частичные страницы не выдаются
за полный набор. Далее истории изменений догружаются последовательно по
уникальному ключу; готовые длительности и история доступны постепенно.
Комментарии/трудозатраты читаются для Динамики и отчётов через существующие
полные загрузчики. Не создавать вторую конкурирующую очередь при переходе
в Динамику; переиспользовать готовые данные, отменять устаревшие операции.

Вариант только с увеличением timeout не уменьшает запрос. Только уменьшение
страницы сохраняет лишние тяжёлые коллекции в первом запросе. Выбрано
разделение этапов, сохраняющее все функции с явной полнотой данных.

## Поведение и ограничения

- Лёгкие поисковые страницы: 50; после timeout один повтор той же страницы
  с размером 25, без сброса уже прочитанных страниц, без повторного включения
  ключей. Дальнейшая ошибка остаётся видимой. Не повторять записи Jira.
- До догрузки «В статусе» показывает «Загружается…», при ошибке/остановке
  объясняет отсутствие истории. Никогда не подставлять updated вместо перехода.
- История не должна изменять подтверждённые более свежие статус/назначение
  и данные другого проекта/эпика/источника. Stop отменяет текущий запрос и
  дальнейшее планирование, Restart и Retry остаются доступны.
- Ошибка тяжёлого этапа не убирает базовую таблицу; повтор читает недостающие
  задачи. Успех скрывает компактный блок; ошибка/отмена оставляет управление.
- Сохраняются фильтры и их черновики, фокус, прокрутка, избранное, раскрытие,
  отдельные Excel/Jira раскладки, даты Динамики и полнота комментариев.
- Excel-синхронизация использует тот же безопасный базовый профиль и последующую
  догрузку. Специализированные проверки статуса/LLM/экспорта продолжают читать
  необходимые полные поля; не менять их семантику общим урезанием API.
- Реальные Jira/LLM запросы не выполняются. Только заглушки и локальный UI.
  Citrix-приёмка остаётся отдельной после передачи управления.

## Проверка результата

Регрессии API (поля/страницы/повтор/отмена), интеграция двух этапов, ошибки
и смена области. Личная браузерная проверка desktop/mobile: базовая таблица
видна до завершения истории, «В статусе» дополняется, открытый фильтр и
прокрутка сохраняются, Stop/Retry работают. Динамика: 1000 задач и
900–1100 событий в день, комментарии и переходы не теряются. Заявлять
уменьшение payload по составу запроса; ускорение прода только после замеров.
