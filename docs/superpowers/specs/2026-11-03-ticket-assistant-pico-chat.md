# Pico: чат для подготовки задачи Jira

## Согласованный результат

Пользователь 03.11.2026 согласовал чат, который извлекает сведения из
разговора, задаёт недостающие вопросы и постепенно заполняет одну карточку
задачи. Автоматическое заполнение можно отменить. Правки шаблона, замена
ручных значений и создание тикета требуют явного действия пользователя.

## Экран и сценарий

- Компактная шапка: проект, шаблон, новый разговор, настройки, полный экран.
- Основная область: сообщения пользователя и Pico. Ввод многострочного текста,
  отправка и остановка. Ошибка оставляет текст и возможность повторить запрос.
- Одна актуальная карточка задачи внутри разговора: тема, тип Jira, описание,
  заполненные дополнительные поля, недостающие сведения. Карточка имеет
  стабильную идентичность; предыдущие ответы не создают действующих дубликатов.
- Кнопки карточки: «Редактировать», «Создать», «Отменить изменение».
  У недоступного создания показана конкретная причина.
- «Редактировать» открывает панель с существующими редакторами полей,
  вложениями и поиском значений Jira. На узком экране панель занимает весь
  экран. Закрытие возвращает к тому же месту разговора.
- Ручная форма и карточка используют один объект задачи. Ручные значения
  защищены от автоматической замены; предложение Pico показывается с
  «Применить» и «Отклонить».
- После успешного создания карточка показывает ключ и ссылку на Jira.
  Повторное создание этой же карточки блокируется существующим механизмом.

Первый ввод может содержать всю задачу или только фрагмент. Pico сначала
извлекает известное и задаёт один следующий содержательный вопрос. Он не
повторяет вопросы, ответ на которые уже есть в карточке или разговоре.
Списки компонентов, версий и других значений ищутся по фактическим данным
Jira. При неоднозначности пользователь выбирает вариант.

Тип задачи берётся из привязки шаблона. Если привязки нет, чат предлагает
доступные типы Jira. Выбранный тип доступен для ручного изменения в форме.

## Шаблоны в разговоре

«Покажи шаблон» выводит точный текущий текст и его привязку к типу Jira.
Просьба изменить правило создаёт предложение с видимыми изменениями и
кнопкой «Применить к шаблону». До применения следующие запросы используют
старую версию. Применение сохраняет новую ревизию личного шаблона и
запускает повторную оценку готовности текущей задачи.

Исключение для текущей задачи хранится в её контексте и не меняет шаблон.
Обязательность полей, разрешения и допустимые значения Jira определяет код
по metadata; текст шаблона не может отменить эти требования.

Шаблоны остаются персональными для пользователя, проекта и origin браузера,
с существующим экспортом/импортом. Общие шаблоны для нескольких сотрудников
потребуют отдельного места хранения и в эту версию не входят.

## Подходы

1. Добавить чат поверх прежнего одноразового prepare: меньше изменений,
   но нет полноценного механизма Pico и последовательной работы инструментов.
2. Использовать Pico/Pi для разговора и существующую модель задачи Jira для
   состояния, редактирования, проверки и создания. Выбранный подход.
3. Полностью заменить редактор и создание агентом: повторная реализация
   уже проверенных сценариев, не дающая нужного преимущества для чата.

## Архитектура

Pico управляет диалогом и вызывает узкие инструменты. Исполнение инструментов
контролируется приложением. Подключение LLM сохраняет существующие настройки;
локальный Codex bridge из КХПД не становится обязательной частью Jira-дашборда.
Совместимость Pi с текущим транспортом проверяется первой. Новый провайдер
и отдельный сервер для дашборда не добавляются.

Адаптер использует существующий `shared.requestText`: ответ модели имеет
проверяемый JSON-конверт с текстом и вызовами инструментов. Это сохраняет
совместимость с текущими chat-completions и Legacy /completions без требования
нативного tool calling у провайдера. Конверт целиком проверяется до выполнения
первого инструмента; результаты каждого вызова передаются обратно Pi.
Токены оцениваются той же консервативной эвристикой, что в shared client.
Локальная проверка резерва ответа не ограничивает генерацию на стороне сервиса.

Сжатие — явное исключение старых завершённых ходов из запроса, без удаления
сохранённой переписки. Текущий ход и пары вызов/результат сохраняются;
актуальное состояние карточки и шаблона добавляется заново. Если оно само
не помещается в бюджет, запрос останавливается с уведомлением.

| Инструмент | Результат и право изменения |
| --- | --- |
| get_task | Текущие поля, вопросы, ревизия и готовность карточки |
| list_fields | Схемы полей выбранного типа, без всех каталогов сразу |
| find_options | Ограниченный поиск допустимых значений с признаком полноты |
| update_task | Проверенный patch локальной карточки; ручные поля идут в предложения |
| read_template | Точный выбранный шаблон и ревизия |
| propose_template_change | Предложение правки; сохранение только через кнопку |
| validate_task | Конкретные недостающие сведения и ошибки допустимости |

У агента нет инструмента создания тикета. «Создать» использует существующий
creator с предварительной проверкой, блокировкой повтора и обработкой
неизвестного результата запроса. Оценки, исполнители и отношения Epic/Sprint
сохраняют текущие правила ручного ввода и проверки.

Карточка, шаблон и история имеют собственные ревизии. Ответ, полученный после
смены проекта, типа, шаблона, новой задачи или ручной правки, не применяется
к другому состоянию. Отмена восстанавливает только последнюю автоматическую
правку при совпадении ревизии; она не отменяет позднейшие ручные изменения.

Описание использует формат, подходящий текущей Jira. Markdown в сообщениях
Pico и содержимое поля description обрабатываются отдельно; HTML из ответа
не исполняется. Предпросмотр карточки должен соответствовать отправляемому
тексту и не обещать поддержку произвольного Markdown в Jira.

## История и ограничения

История сохраняется в персональном хранилище в области проекта и задачи.
Перезагрузка не запускает инструменты, LLM или создание автоматически.
Старые черновики открываются как карточки с предложением продолжить разговор.

В контекст входят правила, выбранный шаблон, актуальная карточка и диалог.
Большие каталоги загружаются инструментами по необходимости. При сжатии
истории текущие поля, ручные правки, открытые вопросы и ревизия шаблона
восстанавливаются из состояния приложения. Сжатие и неполные результаты
обозначаются явно. Существующий бюджет контекста применяется к фактическому
запросу, включая инструкции инструментов. Остановка прекращает цикл и
игнорирует поздние результаты; автоматических бесконечных повторов нет.

## Приёмка

Сценарии на заглушках: запрос ошибки, последовательные уточнения, заполнение
карточки, неоднозначный компонент, ручная правка, предложение её замены,
отмена автоматической правки, просмотр и изменение шаблона, сохранение после
перезагрузки, создание ровно одного тикета, отказ и неизвестный исход Jira.
Отдельно проверяются остановка, ошибка LLM, устаревшие ответы, длинный диалог,
смена проекта/шаблона, вредоносный текст и недоступное хранилище.

Личный UI: 1440 и 390 px, клавиатура, открытие/закрытие редактора, читаемая
карточка и отсутствие горизонтального переполнения. Sol 6.1 Author/Reviewer,
сборка и commit-pinned CDN проверяются до публикации. Прод-приёмка через
testing-citrix-prod отдельно; локальная приёмка не заменяет её.
