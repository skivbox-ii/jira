# Отдельный Pico-дашборд знаний: установка и приёмка

Состояние на 03.11.2026: Tasks 1–4 реализованы; Task 5 добавляет локальную
сборку, проверку совместимости и инструкцию установки. **Публикация,
финальное независимое ревью и полный регресс выполняются контроллером.
Браузерная авторизация Confluence в Citrix и реальный LLM ещё не приняты.**
Локальные ответы модели в тестах — фикстуры, а не проверка реального сервиса.

## Установка после публикации

Создайте отдельный Jira Dashboard и добавьте UJG того же типа, что у импортера.

| Поле UJG | Значение |
| --- | --- |
| Название | Pico — знания Jira и Confluence |
| JavaScript URLs | `https://cdn.jsdelivr.net/gh/skivbox-ii/jira@main/ujg-knowledge-assistant.bootstrap.js` |
| CSS URLs | Пусто: CSS загружает bootstrap |
| AMD module | `_ujgKnowledgeAssistant` |
| HTML to append (если поле есть) | `<div class="ujg-knowledge-assistant"></div>` |

Не добавляйте source/runtime, vendor Pico или preview в список JavaScript URLs.
Bootstrap сам загружает `_ujgCommon.js`, runtime и CSS из одного закреплённого
commit. Дополнительное подключение общего LLM-скрипта не требуется: runtime
содержит `_ujgKA_llmClient`. Runtime AMD — `_ujgKnowledgeAssistantRuntime`;
встроенный Pico — `_ujgKA_picoRuntime`. У помощника задач свои модули.

Версия хранится в существующем `ujg.dashboardReleaseRef`, общем для гаджетов
одного дашборда. Сохранённая версия имеет приоритет над fallback сборки.
На новом дашборде bootstrap разрешает `main`; при недоступности источника
версии применяет fallback. При копировании старого дашборда нажмите
«Обновить версию» на новом дашборде: это сохраняет новый SHA и перезагружает
страницу. Обычная перезагрузка сохранённую версию не обновляет.

## Подключение источников и LLM

1. Откройте дашборд внутри Citrix в текущей Jira-сессии. Jira base/context path
   берётся из UJG API; Jira-запросы идут на текущий origin с session cookies.
2. Используйте уже согласованный Python bridge и SSH-туннель до loopback VDI.
   В настройках виджета укажите **URL bridge**, обычно `http://127.0.0.1:8769`,
   и отдельно **URL Confluence** — настоящий браузерный HTTPS base URL, включая
   context path. Этот адрес используется для ссылок источников, bridge — для чтения.
   Bridge должен разрешать точный Jira origin через CORS и пересылать только
   согласованные GET-маршруты на свой фиксированный Confluence upstream.
   OPTIONS/preflight и локальные сетевые ограничения браузера требуют проверки
   из самой Jira в Citrix. Старый PowerShell HTML-сервер из
   [ранней инструкции](knowledge-bridge.md) не заменяет этот Python bridge.
3. Введите ключи пространств Confluence и проектов Jira в соответствующие
   поля области (списки через запятую). Пустая область запрещает чтение этого
   источника; запрос может только сузить выбранную область.
4. Пользователь вводит свой Confluence PAT в поле настроек виджета и нажимает
   «Применить и проверить». PAT передаётся bridge как Bearer, остаётся только
   в памяти экземпляра вкладки и очищается при уничтожении виджета/перезагрузке.
   Повторно введите PAT после перезагрузки. Его нельзя включать в URL, HTML,
   экспорт, логи или настройки LLM. Настройки и история не содержат PAT.
5. Проверка должна подтвердить JSON от Jira `/rest/api/2/myself` и известного
   пользователя Confluence `/rest/api/user/current`. `/health` этого не доказывает.
   Проверьте поиск и чтение страницы/задачи в выбранной области, затем ссылки
   и фрагменты по оригиналам. 401/403 требуют повторной проверки авторизации.
6. На том же Jira origin используйте **существующее настроенное подключение LLM**
   (общий клиент и прежний провайдер, включая поддерживаемый Legacy режим).
   Виджет читает прежнюю конфигурацию; второго провайдера или отдельного поля
   LLM API key в его настройках нет. При отсутствии конфигурации интерфейс
   предлагает проверить подключение; HTTP-запрос к модели не отправляется.
   Confluence PAT не является ключом LLM. Настройки localhost не переносятся
   автоматически в Jira/Citrix.
7. Только пользователь запускает реальный вопрос, например:
   «Как оформить задачу DevOps по нашим правилам?» Сверьте ответ и каждый
   подтверждённый диапазон с прочитанными оригиналами. История после перезагрузки
   помечена как историческая и не является новым подтверждением источников.

Задействованы только инструменты `search_confluence`, `read_page`, `search_jira`,
`read_issue`. Один поиск выдаёт до 20 источников, фрагмент — до 8000 UTF-16
позиций; продолжение задаётся cursor/offset явно. Неполнота, макросы и
непрочитанные диапазоны обозначаются; вложения и комментарии не заявлены
как прочитанные. Предел хода: 8 вызовов модели / 12 инструментов / 180 секунд.
Контекст по умолчанию 32768, резерв 4096, меняются в настройках.

## Сборка и двухфазное закрепление

Из корня репозитория, без сети и без пересборки vendor:

```sh
node build-knowledge-assistant.js
NODE_PATH=/Users/skivbox/.cache/ujg-ticket-assistant-test/node_modules node --test tests/knowledge-assistant-build.test.js
```

Команда сборки обновляет только `ujg-knowledge-assistant.js`, `.runtime.js`,
`.bootstrap.js`. CSS уже входит в Tasks 1–4. `NODE_PATH` — локальный путь
существующей тестовой среды с jsdom/jquery; на другой машине укажите её путь.
Для вызова общего bootstrap-процесса только для нового виджета:

```sh
UJG_RELEASE_REF=6f8b282 node -e 'const b=require("./build-widget-bootstrap-assets"); const fs=require("node:fs"); const assets=b.buildAssets({widgets:[b.WIDGETS.knowledgeAssistant]}); for(const [file,source] of Object.entries(assets)) fs.writeFileSync(file,source);'
```

`6f8b282` — допустимый **временный fallback первой локальной сборки**; в нём
ещё нет новых generated JS. Не публикуйте этот bootstrap без перепривязки.
Контроллер после проверок коммитит source/runtime/CSS, затем заменяет SHA
ниже на полный hash этого commit (задаёт переменную `ASSET_COMMIT_SHA`)
и выполняет вторую фазу:

```sh
UJG_RELEASE_REF="$ASSET_COMMIT_SHA" node build-knowledge-assistant.js
```

Проверить наличие `.runtime.js`, `.css`, `_ujgCommon.js` в ASSET_COMMIT_SHA,
неизменность source/runtime при перепривязке, diff bootstrap и повторяемость
сборки. Commit второй фазы содержит закреплённый bootstrap. Общая команда
`node build-widget-bootstrap-assets.js` из README пересобирает все виджеты;
для этой задачи применяется scoped вызов выше. Публикация и побайтовая сверка
CDN с commit/runtime/CSS/bootstrap принадлежат контроллеру.

## Доказательства и незакрытая приёмка

- Локальный build-тест загружает оба настоящих runtime в один AMD registry,
  запрещает дубли модулей, создаёт оба гаджета, уничтожает каждый по очереди
  и проверяет работу оставшегося. Два настоящих Pico выполняют фикстурные
  ходы с независимыми историями и продолжают после dispose другого.
- Проверены отдельные имена Pico/LLM, один public/runtime define, точные
  pinned runtime/CSS URL и отсутствие новых literal URL/credential patterns.
  Это ограниченная статическая проверка, не универсальный secret scanner.
- Контроллер ранее подтвердил VDI curl `/health` → 200 JSON через SSH-туннель.
  Это только доступность сервера, **не browser/CORS, Confluence auth или чтение**.
- **Ожидаются:** полный регресс и финальное независимое ревью; двухфазная
  перепривязка, публикация и сверка CDN; проверка браузера Jira в Citrix,
  ввод PAT пользователем, обе identity, поиск/чтение реальных источников,
  пользовательский запуск реальной LLM и сверка ответа/ссылок.

Production-ready не заявляется. Из этой задачи не выполнялись production,
Citrix, внешние HTTP/LLM-запросы или публикация.
